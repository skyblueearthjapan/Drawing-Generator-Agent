## 2. ❗向き判定の方法と、その不確かさ(ディレクターに確認いただきたい点)

2ビュー図面では「左右に並ぶ2つのうちどちらが正面図か」が幾何だけでは決まらない
(右が右側面図なら左が正面図、左が左側面図なら右が正面図で、どちらも第三角法として整合する)。
そこで**3ビューある 4-05 で役割を一意に決め、その社内流儀を他部品へ適用**した。

- 4-05 の人間図面は「中列左(A)・中列右(B)・上段右(C)」の3ビュー。
  Cは**Bの真上**にあるので、`平面図は正面図の上`より **正面図=B**、そしてAは**左側面図**。
  → **この会社は左側面図を正面図の左に置く**。
- この読みを適用すると、円形ビューが左・輪郭ビューが右に並ぶ 3-02 / 6-04 / 7-02 は
  **正面図=輪郭ビュー(軸水平)** となり、AIの選択と一致する(○)。
- 逆に「左=正面図」と読むと3件とも×になり、厳密一致は 1/8 まで落ちる。
- 1-27(広い面が上・板厚が下)と 5-05(輪郭が上・板面が下)は、`平面図は正面図の上`から
  **正面図=下のビュー**となり、AIは上のビュー(=人間の平面図)を正面図に選んでいた(△)。

**確認したいこと**: 実際にこの2ビュー図面で人間がどちらを正面図と呼んでいるか。
ここが確定すると向き正解率が 1/8〜6/8 の幅で動くため、**本報告で最も検証していただきたい箇所**。

## 5. 残る弱点(実測で判明したもの)

### 5.1 ❗М表記の判定ルール「3個以上が円周等配」は厳しすぎる【最重要】

- **1-27**: モデルは二面幅19の六角座+φ12通し。AIは運用ルール(3個以上・円周等配)を満たさないため
  `%%c１２` と書き、対抗仮説「Ｍ１２ナット溶接」は計画コメントに留めた。
  **人間図面は `吊用 ２－%%c１４ 裏面Ｍ１２ナット溶接`** — 対抗仮説が正解だった。
- **4-05**: 立ち上がり板のφ10穴4個(矩形配置)をAIは `４－%%c１０` と書いたが、
  **人間は `４－Ｍ１０深さ１６`**。
- → **判定条件に「六角座/ナット座が付く」「相手が板厚方向に締結される」を足すべき**。
  現行ルールは円周等配だけを見ており、**直線・矩形配置のねじ穴を全て取りこぼす**。

### 5.2 ❗注記の「深さ」はねじ部深さであって下穴深さではない

- **5-05**: モデルのφ8止まり穴は**y=0から29mm**。AIは `Ｍ８深さ２９` と書いたが、
  **人間は `Ｍ８深さ１５`**。29は下穴深さ、15はねじ部の深さ。
- → **モデルの穴深さをそのまま注記に書いてはいけない**。ねじと判定したら
  「ねじ深さ=下穴深さ−(1.5〜2)×ピッチ相当」を人間に確認するか、下穴深さを別に書く運用が要る。

### 5.3 ❗尺度と用紙サイズ: 人間はA3に収めていない

- 1-27 の人間図面は作図範囲が **x≈1600・y≈1100** に及ぶ(A1/2-up図枠)。
  5-05・4-05 も**1枚に2部品**が併記されている。
- AIはA3固定なので 1-27 を1:5、4-05 を1:4 に落とした。**尺度が人間と一致しない**のは
  システム側の制約であって判断ミスではない。→ **A2/A1図枠の用意が次の律速**。

### 5.4 寸法セットの食い違いの型

| 型 | 例 | 件数 |
|---|---|---|
| 中心線基準 vs 全体寸法 | 人間 `149`+`149` / AI `298`(1-27) | 多数 |
| 端面からの位置を人間は入れる | 人間 `20`(端→皿穴)・`236`(端→吊穴) / AIは無し | 1-27で2件 |
| 角度寸法(位相)を人間は入れる | 3-02 の `20%%d`/`70%%d`/`90%%d` | 3件 |
| AIが幾何完全性のために足した寸法 | `R3.2`(曲げR)・`19`(二面幅)・`6.4` | 過剰の主因 |
| 人間が面取り・小R を明示 | 5-05 の `R8.5`・`17`・`45%%d` | 5-05で多数 |

## 8. 工房ループ(`app/workshop.py`)の実戦所見

### 良かった点
- **状態機械が10依頼で破綻せずに回った**。`new` → `scan`(計測→候補→計画待ち) →
  choice/plan投入 → `scan`(生成→ゲート→納品) → `retry`(2件)まで通しで動作。
- **`retry` が実戦で効いた**。5-05・4-05 の不合格を巻き戻して1回で回収。
  第1弾の要望(§7-1)が正しく実装されている。
- **不合格理由サマリが役に立った**。5-05 は `未指定計1件[位置(X軸)未指定1件(例:X=-98)]` の1行で
  原因(片側だけの寸法)が特定できた。第1弾の要望(§7-2)も解決済み。
- **台帳は依頼IDでupsertされ、10行が1部品1行で保たれた**(第1弾の重複問題は解消)。

### ❗不具合・改善要望(優先度順)

1. **❗サブプロセスのタイムアウトが実機の遅さに対して短すぎ、10件中9件が全滅した**。
   `measure_3d.py` が1部品 **285〜822秒**かかるのに旧 `timeout=180` で、
   全件が「計測中」に張り付いた。原因は**SW形状APIの1呼び出しが100〜300ms**(素のCOMは0.0ms)
   という機械側の遅さで、スクリプトの欠陥ではない。
   → 本テストでは `app/workshop.py` のタイムアウトを定数化して拡大した
   (`TIMEOUT_MEASURE=1800` 等、環境変数 `OMC_WS_TIMEOUT_SCALE` で倍率変更可)。**恒久化を推奨**。
2. **❗タイムアウトで中断すると SolidWorks にインポート部品が開いたまま残る**。
   3件が残留し、次の計測を遅くした。→ **scan側に「起動時の孤児ドキュメント掃除」を入れるべき**

## 11. 測定の作法(第1弾からの変更点)

- **計画を書く前に `ledger.py`(scratchpad)でゲート②が見る特徴台帳を先読みした**。

- 尺度は寸法帯の予算式から決めた(§4-4)。
- 穴注記の `attachment` はディレクター指示どおり **全件 `bottom-left` に統一**した
  (dim_engineの文字枠推定が bottom-left 前提である既知欠陥の回避)。

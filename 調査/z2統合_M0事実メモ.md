### 2.3 claim API — **最初の状態が `reading` 固定**

`phase2/app/db.py:327-356` `claim_next_queued()`:
```sql
BEGIN IMMEDIATE
SELECT * FROM jobs WHERE status='queued' ORDER BY created_at ASC, id ASC LIMIT 1
UPDATE jobs SET status='reading', stage_note=? WHERE id=? AND status='queued'
COMMIT
```
- 排他: `BEGIN IMMEDIATE`(db.py:331)。二重クレーム防止は `WHERE ... AND status='queued'`
- 順序: `created_at ASC, id ASC`(先着順)
- **クレーム可能な状態は `queued` のみ** → `cancelled`/`held` は二度と拾われない(v3.3 の設計意図)
- ❗**遷移先 `'reading'` が SQL にハードコード**(db.py:342, 347)。
  kind によって最初の状態を変えることは、この関数を書き換えない限りできない。
- claim はリトライ禁止(`phase2/worker/api.py:140` に「queued→reading は応答前にコミット済み」)

## 8. 差異・リスク(手順書の想定 vs コードの現実)

### ★リスク1(最重要): DXF だけの納品は現行コードでは**永久に承認できない**

`has_deliverable()`(`phase2/app/server.py:641-652`)は `results.step` / `results.sldprt` だけを見る。
`/approve` は偽なら無条件 409(server.py:664-672)。UI 側も `canApprove`(index.html:1308)で
承認印を出さない。**締めをサーバに置いた v3.3(2) の設計そのもの**が、drawing を弾く。

- 手順書§M2「承認は DXF が納品箱に実在しなければ 409」は**方向として正しいが、
  `has_deliverable()` の kind 対応が必須**という具体が抜けている
- さらに現行は `results` の**値が入っているか**しか見ておらず、**ファイルの実在は確認していない**
  (実在確認をするのは blocker の figures 側 pipeline_real.py:776-808 だけ)。
  手順書§M2 の「納品箱に**実在**しなければ409」を満たすには**実在チェックの新規実装**が要る
- 対応案: `has_deliverable(job)` を kind 分岐にし、drawing は
  `results.dxf` の値**かつ**`納品箱/{job_id}/{その名前}` の実在を見る

### ★リスク2: `prompts.yaml` の `stages:` に drawing 段を足すと**工房が全停止する**

`load_prompts()` の `expected = ["reading","verifying","building","inspecting"]` 完全一致検査
(`phase2/worker/pipeline_real.py:168-173`)。不一致で `ValueError` → `make_pipeline()`
(runner.py:34-44)がワーカー起動時に落ちる。
`prompts.yaml` は**ワーカー起動時に1回だけ読まれる**
(引き継ぎ書_2026-08-06:277-279)ため、**気づくのは再起動時**。
見張り(5分間隔)が蘇生を試み続けて失敗するので、**2D→3D も含めて工房が止まる**。

- 手順書§M3-1「プロンプトは prompts.yaml に drawing 用ステージを足す」を字義どおり
  実行すると事故る
- 対応案: v3.4 の `sixview:`(prompts.yaml:368-475)と同じ**最上位の別キー `drawing:`** に置く。
  この方式なら `stages:` を一切触らないので既存フローの回帰リスクがゼロ

### ★リスク3: 状態名を新設すると波及が広い(手順書§M2 の状態機械案は要再検討)

手順書§M2 は `queued → measuring → orienting → planning → drafting ⇄ checking → …` を提案。
これを字義どおり実装すると、以下**全て**を同時に直す必要がある:

| 波及先 | file:line |
|---|---|
| `STATUSES` に追加 | `phase2/app/db.py:24-43` |
| `ACTIVE_STATUSES`(**2ファイルに重複**) | `phase2/app/db.py:46` と `phase2/worker/config.py:30` |
| claim の遷移先が `'reading'` 固定 | `phase2/app/db.py:342, 347` |
| 中断復帰 | `phase2/worker/runner.py:170, 178` |
| control の可否判定 | `phase2/app/server.py:734, 839, 857, 902` |
| UI の4マップ | `index.html:925, 926, 1554, 1876` |

うち `claim` の `status='reading'` ハードコードは、**drawing の最初の状態を変えられない**
ことを意味する(claim 直後にワーカーが即 update する回避策はあるが、
claim〜update の隙間で UI に「読解中」と出る)。

- **提案(承認事項)**: 状態名は**増やさず**、既存5状態へ写像する。
  例 `reading`=計測、`verifying`=向き選択、`building`=投影+作図計画、`inspecting`=生成・検査。
  UI は `kind` を見て `STAGE_NAMES` の**表示名だけ**差し替える(index.html:927 のみの変更)。
  → 波及が UI 1箇所+ワーカー分岐だけに縮む。`cancelled/held/restart/差し替え`が
  そのまま効くことも自動的に保証される(手順書§M2 の要求そのもの)

### ★リスク4: blocker への図の必須化 と 質問票に図が無いこと

`_blockers_without_figures()`(pipeline_real.py:776-808)は納品箱にファイルが実在するかまで
機械照合し、欠けたら**検査ステージだけをやり直す(上限1回)**。
DGA の `質問票.md` には図が無い(§7.5)。
→ drawing の fuda は**毎回1回むだな再検査**を起こす。
対応案: (a) drawing の blocker を図必須の対象外にする(実装契約.md:268 が
`topic` が「運用:」で始まるものを除外している前例がある)、または
(b) DGA 側が候補PNG・生成PNG を figures として添える。
**(a) を初版、(b) を M6 送り**が現実的。

### リスク5: `app/tests` の流儀が安全規約§5-1 に反する

### リスク6: DGA 側の CLI 契約が機械判定に耐えない

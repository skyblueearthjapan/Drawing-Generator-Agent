## 2. 向き選定の分析 — ここが最大の弱点

### 2.1 「候補6件」が人間の選択を被覆しなかった 3/10

|図番|人間の選択|候補集合に有ったか|
|---|---|---|

CLAUDE.md は「上位6候補で90%被覆」としていたが、**本バッチでは70%**だった。
特に **`+180` 回転が候補集合から完全に抜けている**のは構造的な穴で、
円板(3-09)のように「どちらを上にするか」だけが問題になる部品を原理的に当てられない。

### 2.2 AIオペレータ(私)の判断ミスの型

3件の×は全て **「私が事前分布1位(`*正面`+0)を形状論で上書きして外した」** という同じ型だった。

- **3-04 ベアリングケース**: 「軸受箱の定義的特徴は穴だから、穴が円に見えるビューを正面に」と判断
  → 人間は **取付ボルトが見える面(=`*正面`+0)を正面**にし、穴の円形ビューは**平面図**に置いた。
- **7-06 LSブラケット**: 「最大面(100×61)に穴が集中しているから正面」と判断
  → 人間は **曲げ形状が見える立面(=`*正面`+0)を正面**にし、最大面は**平面図**。
- **2-06 モータフランジ**: 「t43/φ222=0.19 の円板だから円形ビューが主投影図」と判断
  → 人間は **JIS B0001 の加工姿勢どおり主軸を紙面水平**にした断面を正面図にした。

→ **教訓A**: 情報量の多い面は「正面図」ではなく「平面図/側面図」に置かれることが多い。
「一番情報の多い面を正面に」というJIS流の読み替えは**この会社の流儀では誤り**。
→ **教訓B**: 旋盤物は t/D 比に関係なく **例外なく主軸を紙面水平**にする(2-06・5-04 とも軸水平)。
  私は 2-06 で「円板だから例外」と判断して外した。**例外を作らない方が当たる。**

不合格の原因を分類すると、**私の計画の問題**と**エンジンv1の構造的限界**に割れる。

### 3.1 エンジンv1の構造的限界(計画をどう書いても通らない) — 主因

| 分類 | 該当 | 内容 |

| **角度配置のPCD穴群** | 2-06/4-07/6-02/5-04/3-04 | 12穴PCD129のように**円周等分**に並ぶ穴は、中心が `R·cos15°`= 62.302… のような**非丸め座標のX/Y位置ノード**を生む。gate2は位置ノードを軸方向の寸法チェーンでしか到達判定しないため、**1本のPCD寸法では1組(2個)しか固定できない**。12穴なら X軸だけで3本、X/Y合わせて6本の「無意味な弦寸法」が要る。**人間はPCD1本で済ませている**。 |

### 3.2 私(AIオペレータ)の計画の問題 — 修正可能

- **「対称な特徴間の距離」ばかり入れて、基準面からのチェーンを作らなかった**。

## 7. 工房ループ(`app/workshop.py`)の実戦所見

### 良かった点
- **状態機械が期待どおり効いた**。10依頼を1コマンドで「計画待ち」まで一括前進、
  choice.json 投入後に再scanで自動 materialize、plan.json 投入後に再scanで生成→ゲート→納品まで走った。
- 1依頼の失敗が他に波及しない(`advance_one` の例外握り潰しが機能)。TEST-BROKEN-001は
  必須項目不足で「受付済」に留まり続け、他9件の処理を妨げなかった。
- 納品箱への複製と解釈レポート雛形の自動生成まで通しで動いた。

### 不具合・改善要望(優先度順)
1. **❗不合格からの再試行手段がCLIに無い**。`不合格` は終端状態なので、計画を直しても
   `scan` では二度と動かない。今回は `status.json` を手で `生成中` に書き戻した。
   → **`python app/workshop.py retry <依頼ID>` を追加すべき**(履歴に再試行を残す)。
2. **不合格理由が要約されず全件JSONで出る**。未指定132件が並ぶだけで原因分類ができない。
   → `不合格理由.json` に「円/位置」「軸別」「PCD由来か面取り由来か」の**集計サマリ**を付ける。
3. **尺度がCLIから指定できない**。A3に入らない部品(1-04・6-02)は `依頼.json` の `尺度` を
   人が書き換えるしかなかった。→ bboxとビュー集合から**尺度候補を自動提案**する段が要る。
4. **ゲート③(目視)が状態機械に無い**。PNGは出るが誰も見ない。
   → `目視待ち` 状態を作るか、少なくとも `status.json` に「PNG未確認」を残す。
5. **`計画待ち` のまま何日でも止まる**。AIオペレータ待ちであることは正しいが、
   `status` 表示に「何を待っているか(choice/plan/質問票)」を出すと運用しやすい。
6. 台帳が**生成のたびに追記**されるため、再試行すると同一図番が複数行になる(今回4図番が重複)。
   → `--no-ledger` を再試行時の既定にするか、同一図番は追記でなく更新にする。

### ❗ゲート③(目視)で見つけた実害 — 寸法が表題欄に重なる
納品した3件のPNGを目視したところ、**5-08 で下側の寸法(16 / 21 / 38)が表題欄の上に載っていた**。
原因は `plan_schema.md` §1.3a が自ら限界として挙げている
「**紙面中央への配置をビュー幾何だけで計算し、外周の寸法帯を含めない**」ことで、
実害として確認できたのは今回が初。`layout.collisions` にも出ない
(衝突判定はビュー同士と注記のみで、**図枠・表題欄との衝突を見ていない**)。
→ **改善案**: `_layout_targets` の利用可能領域を「ビュー幾何 + 各辺の予約帯」で取り、
  さらに `layout.collisions` に**図枠/表題欄ゾーンとの交差**を追加する。
  4-12・7-06 は寸法段数が少なく偶然かわしていただけで、同じ欠陥を抱えている。

### 照合ツール(compare_views)側の新しい罠

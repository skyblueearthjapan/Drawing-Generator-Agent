## 1. 手法概要

1. `荏原トライ調整用/DXF/部品表用DXFデータ/<軸>/*.dxf` のうち組立図(`-00`, `全体図`)を除く
   **部品図190枚全数**を対象に、表題欄の固定ラベル `TEXT '品名'` の座標をキーにして
   グループ化(=「図枠バケツ」)した。
2. 最頻出バケツ(後述の「バケツA」、190枚中80枚=42%、**9軸フォルダ全部に出現**)から
   9軸フォルダ×2枚=**18ファイル**をサンプリングした(`調査/sample_files.py`)。
3. 各ファイルのmodelspace全エンティティを「タイプ・レイヤ・色・線種・座標(丸め6桁≒1e-6)・
   内容(TEXT/MTEXTは文字列も含む)・文字スタイルの実体(フォント名・幅係数・斜体角。
   スタイル名そのものは使わない)」からなるシグネチャに変換し、**18ファイル全てに
   完全一致で出現するシグネチャの集合=図枠**とした(`entity_sig()` in `extract_common.py`)。
4. 位置(座標・スタイル実体・文字高)は18ファイル全てで一致するが内容(text)だけが違う
   エンティティを「可変フィールド候補」として別途抽出した。
5. 3.の共通集合に該当する実エンティティを基準ファイル(`25154-1-07_走行ギア.dxf`)から
   `ezdxf.addons.importer.Importer` で複製し(レイヤ・線種・文字スタイル・ブロック定義を
   自動解決)、`図枠/frame_template.dxf` として保存した。

## 2. 重要な発見: 「図枠バケツ」— 用紙サイズ・尺度で座標がスケールする

最初、9軸フォルダから無作為に18枚(各サイズ混在)を選んで完全一致抽出を試みたところ、
**共通エンティティはわずか4個(すべてINSERT)** しか見つからなかった。原因を調査した結果:

- 同じ会社の同じ表題欄レイアウトでも、**用紙サイズ(=部品の大きさに応じて選ばれる図枠サイズ)
  によって表題欄・外枠の絶対座標が変わる**。全190部品図で `TEXT '品名'` の座標をキーに
  分類すると **34種類のバケツ**が存在した。
- 例: `TEXT '品名'` が `(220.24, 27.41)` にあるファイル群(外枠 410×287mm)が最頻出(80枚)。
  `(439.47, 53.82)` にあるファイル群(外枠 820×573mm相当)は11枚。`(1754.88, 212.27)`
  (巨大フレーム用)は9枚、というように用紙が大きくなるほど原点からの絶対距離も大きくなる。
- **尺度(1:1, 1:2, 1:5, 1/1.5等)とバケツは必ずしも1対1ではない**。同じバケツ内でも
  尺度ラベルの値は「1:2」「1:1」など複数出現する(=尺度は表題欄座標を決める要因ではなく、
  純粋に記入内容としての可変フィールド)。座標を決めているのは**選択された用紙サイズ**である。
- 結論: **図枠は「1つ」ではなく、用紙サイズごとに複数の座標バリアントが存在する**。
  本フェーズでは最頻出・全軸フォルダ横断的に出現するバケツA(以下「本テンプレート」)を
  代表として抽出した。他バケツも同様の抽出手順(`調査/extract_common.py` の
  `SAMPLES` を差し替えるだけ)で追加テンプレート化できる。**他バケツのテンプレート化要否は
  ディレクター判断が必要**(質問票 Q1 参照)。

## 3. 図枠(共通・固定)エンティティ = 113個

`図枠/frame_template.dxf` に格納。バケツA(18サンプル)全てで完全一致(座標誤差 < 1e-6)。

| タイプ | 個数 | 内容 |
|---|---:|---|
| LINE | 68 | 外枠・表題欄・REVテーブルの罫線(layer 254中心、一部 layer 1/2) |
| MTEXT | 27 | 固定ラベル・記号(「ＲＥＶ」「株式会社」「ラインワ－クス」「第三角法」「Ａ３」「ｋｇ」「品番」等)およびREV/締結部材ミニ表の未使用プレースホルダ(「＊」「＊＊」) |
| TEXT | 10 | 固定ラベル(「品名」「図番」「重量」「装置名」「尺度」「図枠」「製図」「審査」「更新」「製作番号」) |
| INSERT | 5 | 図枠内蔵ブロック(第三角法アイコン=BLOCK002、会社ロゴ様マーク=BLOCK004、注記ブロック=BLOCK005、単位/凡例タグ=BLOCK006/007。いずれも insert=(0,0) scale=1) |
| LWPOLYLINE | 1 | 外枠本体(閉曲線、4頂点、`(5,5)-(415,5)-(415,292)-(5,292)`、layer 1、色7=白) |
| POINT | 1 | 外枠右上コーナーの基準点 `(415,5)`、layer 1 |
| CIRCLE | 1 | シート左上コーナーの丸マーク(中心 `(19.324,278.844)` 半径10、連番マーク用の枠) |

外枠サイズ: **410mm × 287mm**(バケツA)。実座標は `(5,5)` 〜 `(415,292)`。

### 色の使われ方
全レイヤの `LAYER.color` は形式上すべて `7`(白)で、**実際の色分けはエンティティ個別の
`color` 属性で行われている**(BYLAYERを引いても意味がない)。図枠内では:
- 色3(緑): 外枠内側の表題欄・REVテーブル罫線と大半のラベル(58/68のLINE、11/27のMTEXT、
  10/10のTEXT)
- 色7(白): 外枠本体(LWPOLYLINE)、一部のMTEXT(「ｋｇ」等の単位表記)
- レイヤ名は `'0'〜'255'` と `'Defpoints'` の**ACIカラー番号そのもの**で、レイヤ名自体に
  意味的分類(寸法線/隠れ線等)は無い。図枠は主に layer `254`(表題欄本体)と `1`(外枠・
  一部基準点)を使う。

## 4. 可変フィールド = 15個(`図枠/fields.json`)

抽出手法: 「位置・文字高・スタイル実体は18ファイル全てで一致するが、内容(text)が
異なる」エンティティを機械抽出(9個)。加えて手動で以下を確認・追加(合計15個):

| field | 内容 | 発見方法 |
|---|---|---|
| 品名_値 | 部品名(例: 走行ギア) | 機械抽出 |
| 装置名_値 | プロジェクト名(例: ラインマン200) | 機械抽出。本データセットでは全サンプルで実質同一値(同一号機のため) |
| 図番_値 | 図番(例: 25154-1-07) | 機械抽出 |
| 尺度_値 | 縮尺表記(例: 1:2, 1:1) | 機械抽出。表記ゆれあり(`1:1.5` と `1/1.5` が混在) |
| 品番_番号 / 品番_仕様 / 品番_個数 | シート右下の締結部材ミニ表(ボルト規格等、最大1行) | 機械抽出 |
| REV_日付_2 / REV_日付_3 | 変更履歴テーブル2/3行目の日付 | 機械抽出。1行目は18サンプル全てで未使用プレースホルダ`＊＊.＊＊.＊＊`のため「共通(113)」側に混入している(=1行目は本テンプレートでは実質固定扱い) |
| 製図者_氏名 | 製図欄の氏名 | 準機械抽出。1e-6厳密一致では18枚中1枚が0.047mmずれていて機械抽出から漏れた(位置は実質固定、原データの手打ちノイズと推定) |
| 重量_値 | 重量(kg) | **未実測・位置推定**。バケツA(80ファイル全数)を検索したが数値記入例が1件も見つからなかった。「重量」ラベルは表題欄に固定であるが、値セルへの記入は本データセットでは未運用の可能性が高い。位置は品名/装置名ラベル→値のオフセット規則(dx≈+4.0,dy≈-5.1)から推定した座標を記載。**要ディレクター確認**(質問票 Q2) |
| 連番マーク_値 | シート左上の丸(共通・固定)内に入る2桁連番。図番末尾と一致 | 手動発見。丸の中心は固定だがMTEXT自体はCENTER系配置のため文字幅で挿入基準点がわずかに動き、機械抽出の位置一致判定から漏れていた |
| 材質個数ノート_自製品 / 材質個数ノート_購入品 | シート左上の自由記述ノート。自製部品は「材質/個数」2行、購入部品は「メーカー/品名/型式/個数」4行(排他利用) | 手動発見。行数がテンプレートにより変わるため機械抽出の対象外だった |
| 用紙サイズ | 本バケツでは"Ａ３"固定 | 表題欄内にMTEXTとして直接同梱(=共通113個の一部であり、フィールドというより定数) |

### 重要な発見: 「材質」に専用セルが無い
CLAUDE.mdの要求フィールド一覧に「材質」が含まれるが、**この表題欄レイアウトには
「材質」という専用ラベル/セルが存在しない**。材質情報は、シート左上の自由記述ノート
(`材質個数ノート_自製品`)内に `材質　○○○` という形でテキストとして書き込まれている
(位置はほぼ固定だが厳密な1セルではなく複数行ノートの一部)。この点は仕様上の想定と
ズレる可能性があるためディレクター確認が必要(質問票 Q3)。

## 5. 文字スタイル(STYLE表)

- ラベル文字(TEXT型の固定ラベル)は全て `STANDARD1` スタイル(font=`TXT`, bigfont=`BIGFONT`,
  width=1.0)。
- MTEXT(値・注記)は `GMM001, GMM002, ...` という**ファイルごとに採番し直される連番スタイル**
  を使う。フォントは全て `txt.shx` / `bigfont.shx` で共通、差異は `width`(文字幅係数、
  0.39〜1.09の範囲)のみ。**スタイル名でファイル間比較すると誤判定するため、本分析・
  `engine/frame_extract.py` では `(font, width, oblique)` の実体タプルで比較している。**
  後工程でDXFを新規生成する際も、スタイル名の一致ではなく実体プロパティで判断すること。

## 6. 寸法スタイル(DIMSTYLE)概要

- テーブルには `STANDARD` + `GMM001〜GMM0xx`(ファイルごとの寸法個別スタイル)が存在。
- 主要変数(`25154-1-07_走行ギア.dxf` の例、22個のDIMENSIONの大半が該当):
  - `DIMTXT`(文字高) = 4.0mm
  - `DIMASZ`(矢印サイズ) = 3.0mm
  - `DIMEXO`(延長線オフセット) = 1.0mm
  - `DIMEXE`(延長線オーバーラン) = 2.0mm
  - `DIMGAP`(文字とのギャップ) ≈ 0.5(寸法ごとに微調整され0.39〜0.66の幅で揺れる)
  - `DIMDEC`(小数桁) = 2 または 4(寸法により異なる)
  - `DIMTAD` = 3(文字を寸法線の上に配置)
  - `DIMCLRD`(寸法線色) = 3(緑)
  - `DIMLFAC`/`DIMSCALE` = 1.0
  - `DIMTXSTY` = `GMM002`(実体はTEXTスタイルと同じ`txt.shx`系)
- **フェーズ3(寸法記入エンジン)への申し送り**: 寸法ごとに専用DIMSTYLEが1個ずつ
  生成される運用のため、新規生成時も「都度DIMSTYLEを複製してDIMGAP等を微調整する」方式を
  踏襲するか、共通スタイル1本に統一するかは設計判断が必要。本フェーズでは深追いしていない。

## 7. コードページ・単位・その他ヘッダ

- `DXFVERSION` = `AC1015`(全ファイル共通)
- `$DWGCODEPAGE` = `ANSI_932`(Shift-JIS)。ezdxf上は `doc.encoding == 'cp932'`。
  **`ezdxf.new()`で新規docを作る際、`doc.header["$DWGCODEPAGE"]`を書き換えるだけでは
  不十分で、`doc.encoding`属性(Pythonレベルの内部状態)を明示的に合わせないと
  `saveas()`時に`$DWGCODEPAGE`が`ANSI_1252`へ上書きされる**(ezdxf.document.Drawingの
  save処理が`self.header["$DWGCODEPAGE"] = tocodepage(self.encoding)`を実行するため)。
  `frame_template.dxf`生成では`doc_new.encoding = doc_src.encoding`を明示している
  (`調査/build_frame_template.py`参照、後工程でも同様の対応が必要)。
- `$INSUNITS` はヘッダに明示されていない(未設定)。座標は実寸mmとして扱われている
  (外枠410×287等、部品の実測寸法と桁がそのまま対応する)。
- `$LTSCALE` = 8.4(全サンプル共通)。

## 8. 検証結果

### 8.1 エンティティ数ラウンドトリップ
`frame_template.dxf` を`ezdxf.readfile()`で読み戻し、modelspaceのエンティティ数が
**113個**であることを確認(抽出時の共通集合サイズと完全一致)。

### 8.2 目視確認
- `図枠/render_check.png` をReadツールで直接目視。外枠矩形・表題欄グリッド・REVテーブルの
  罫線・左上の丸マークが、元ファイル(`25154-1-07_走行ギア.dxf`)の同領域のレンダリング
  (`調査/ref_zoom.png`)と**行・列の位置関係が一致**していることを確認した。
  (文字グリフはmatplotlib側の日本語フォント設定の制約で正しく描画されないため、
  グリッド構造・線の位置での比較を主とした。)

### 8.3 図枠差し引きテスト(`engine/frame_extract.py`)
`subtract_frame(doc)` を3つの独立したファイル(基準ファイルと異なる軸フォルダ含む)に
適用し、いずれも **`frame_matched: 113`(=全113個が過不足なく一致)** を確認した:

| ファイル | total | frame_matched | remaining |
|---|---:|---:|---:|
| `1.走行軸/25154-1-07_走行ギア.dxf`(基準ファイル) | 265 | 113 | 152 |
| `5.ひねり軸/25154-5-08_メカストッパー受け.dxf` | 16069 | 113 | 15956 |
| `S2 POS旋回軸/25154-S2-05_押しボルト座.dxf` | 168 | 113 | 55 |

`25154-1-07_走行ギア.dxf`の残余152個(部品作図+寸法22+リーダー2+可変表題欄MTEXT等)を
レンダリングし(`調査/remaining_1-07.png`)、外枠・表題欄グリッド・固定ラベルが
過不足なく除去され、部品の投影図・寸法・注記・可変フィールドの実データ(品名の値
「走行ギア」等)が正しく残っていることを目視確認した。**取りこぼし(=図枠なのに残った)
や取りすぎ(=部品側なのに消えた)は確認されなかった。**

一点、REVテーブル内の「最新リビジョン強調枠」と思われる小さな矩形(LWPOLYLINE、赤色)が
ファイルによって残余側に出ることがある。これは行位置がリビジョン件数に応じて動く
可変要素であり、想定通りの挙動(=正しくは可変扱い)と判断している。

## 9. 後工程(部品ビュー+寸法合成)への申し送り事項

1. **座標系**: 図枠はミリメートル実寸。バケツAの外枠は `(5,5)-(415,292)`
   (410×287mm)。部品ビューはこの矩形の内側、表題欄(y=0〜約29)より上の領域
   (おおよそ `y: 29〜292`)に収める必要がある。
2. **図枠バケツの選択ロジックが必要**: 部品の投影サイズに応じて、どの用紙サイズ
   バケツ(=どのテンプレート)を使うかを決めるルールが要る。本フェーズでは
   バケツAのみテンプレート化済み。他バケツは同じ手順(`調査/extract_common.py`の
   `SAMPLES`差し替え)で追加抽出できる。
3. **フィールド書式**: MTEXTの`\T1.000000;`等の書式コードは意味を持つ(文字間隔)ため、
   新規生成時も先頭に同じprefixを付けること。`fields.json`の`mtext_prefix`を参照。
4. **スタイル名は使い回さない**: `GMM0xx`はファイルごとの連番。新規生成時に既存の
   `GMM0xx`名をそのまま参照すると別ファイルでは無関係のスタイルを指してしまう恐れがある。
   `frame_template.dxf`に同梱されているスタイル実体(font/width/oblique)を基準に、
   新規ドキュメントごとに改めてスタイルを解決/複製すること。
5. **重量欄・材質欄は「型どおりの記入例」が乏しい**: 重量は本データセットでほぼ未記入、
   材質は専用セルが無く自由記述ノート。仕様(「重量=SW質量特性から自動算出」)を
   実現するには、フィールド位置は`fields.json`の推定値をベースに、実際にどう見せるか
   (書式・桁数)をディレクターと合意してから固める必要がある。
6. **`engine/frame_extract.py`の`subtract_frame()`は本テンプレート(バケツA)専用**。
   他バケツのファイル/生成物に適用すると`frame_matched`が0に近くなる(座標が合わないため)。
   複数バケツに対応する場合は`load_frame_signatures()`にバケツ別テンプレートを渡す形で
   拡張できる設計にしてある。
7. **コードページ/エンコーディングの罠**(7章参照)は他のDXF生成コードでも必ず踏むので、
   `doc.encoding`を明示設定する一行を`engine/`の共通ヘルパに入れておくことを推奨する。

## 10. 質問票(未解決の疑問)

**Q1. 図枠バケツは何種類テンプレート化すべきか?**
全190部品図で34種類の「品名ラベル座標バケツ」が存在する(=用紙サイズの選択肢が34通り
という意味ではなく、丸め誤差や特殊レイアウトも混ざっている可能性がある)。実務上よく
使う用紙サイズ(A4/A3/A2/A1相当)がどれで、フェーズ2以降のパイプラインが対応すべき
バケツ数はいくつか、ディレクターの判断を仰ぎたい。参考: 上位5バケツで190枚中123枚
(65%)をカバーする。

**Q2. 重量欄は実際に使われているか?**
バケツA(80ファイル)を全数走査したが、表題欄の「重量」ラベルに対応する数値記入エンティティ
が1件も見つからなかった。紙図面には手書きで追記される運用なのか、単に本データセットの
対象部品(比較的小物)では重量記入を省略しているだけなのか、確認したい。前者であれば
自動算出値をDXFに書き込む方針で問題ないが、後者であれば「あえて空欄にする」運用ルールが
背後にある可能性がある。

**Q3. 「材質」フィールドの扱い**

# フェーズ2.5 実行レポート — 図枠合成(engine/compose_drawing.py)

実施日: 2026-08-09 / 環境: Python + ezdxf 1.4.4 + matplotlib(Agg, Meiryo)

## 0. 結論

**図枠テンプレート + SWビュー投影DXF(フェーズ2出力) + 表題欄記入 の合成に成功した。**
`生成図面/TEST-001_ホルダー.dxf`(AC1015/cp932/実寸1:1・A3・第三角法4ビュー・表題欄記入済み)と
そのプレビュー `生成図面/TEST-001_ホルダー.png` を出力した。検証は数値5項目すべて合格、
目視でも図面として成立していることを確認した(詳細は下記)。

## 1. 成果物

| パス | 内容 |
|---|---|
| `engine/compose_drawing.py` | 合成エンジン本体。`compose(views_dxf_path, meta_json_path, fields, scale, out_path)` が再利用可能な公開API。`render_png()` はPNG化ヘルパー |
| `生成図面/TEST-001_ホルダー.dxf` | 成果物DXF(205エンティティ = 図枠113 + ビュー82 + 記入10) |

`_main()`(CLI実行, `python engine/compose_drawing.py`)が上記2成果物を生成する実行スクリプトを兼ねる。
入力は `調査/phase2_out_15015-P3-013_ホルダー.dxf` + `調査/phase2_meta_15015-P3-013_ホルダー.json`
(フェーズ2実測データ、ホルダー φ75×L40)。

## 2. 処理内容

1. **図枠土台**: `図枠/frame_template.dxf` を `ezdxf.readfile()` でそのまま読み込み(新規docではなく
   既存docを土台にすることで113共通エンティティを無改変のまま保持)。`doc.encoding="cp932"` /
   `$DWGCODEPAGE`を明示維持(CLAUDE.md知見どおり)。
2. **ビュー取り込み+再配置**: ビューDXFの全82エンティティを `meta.views.<key>.outline_mm` で
   4ビューへ領域分類(bboxの中心点がどのoutline矩形に入るかで判定。6ペア全て重なりゼロという
   フェーズ2の実測結果を前提にした決定論的な分類)。
   **設計判断(申し送り重要)**: フェーズ2のビューはA1シート(841×594mm)上に**ビュー間ギャップ40mm**で
   配置されていた。これをそのまま「グループとして平行移動」するとA3の作図可能領域
   (410×262mm)に収まらない(4ビュー全体のoutline外接矩形は208.8×270.7mm。A3側の余白は
   262mmしかなく、ギャップだけでもmm単位で数十mm超過する)。そこで **第三角法の相対整列
   (front/top同一x中心・front/right同一y中心)を保ったまま、ビュー間ギャップを40mm→15mm
   (`VIEW_GAP_MM`)に詰め直して新しい中心座標を再計算**する方式を採用した。
   各ビューは「(元の幾何中心)→原点→scale倍→(新しい中心)」の`Matrix44.chain`変換を
   `entity.transform()`で適用(ezdxf 1.4のDXF実体はtransform()を持つため、Importer取り込み前に
   ソースdoc上のエンティティへ直接適用してからコピーする設計)。
   結果、scale=1.0(実寸)のままでも4ビュー全体は136.3×198.2mmに収まり、
   図枠の表題欄・左上ノートいずれとも重ならずに配置できた(検証④参照)。
3. **線種の保証**: `Importer.import_table("linetypes", entries=[...])` で `HIDDEN`/`PHANTOM`/`CENTER`
   を明示的に図枠doc側へ先出しコピーしてから`import_entities()`する
   (`_ensure_linetypes()`。通常はImporterがエンティティ参照から自動解決するが、要件どおり
   明示チェック+補完のコードを入れた)。
4. **表題欄記入**: `図枠/fields.json` の各フィールドのアンカー・スタイル(font/width_factor/oblique)・
   `align`(attachment_point)に従って `MTEXT` を追加。STYLEはCLAUDE.md知見どおり
   「名前でなく実体(font, width_factor, oblique)」で図枠doc内の既存STYLEと照合し、
   一致するものがあれば再利用、無ければ新規追加(`_ensure_style()`)。
   記入した10フィールド: 品名_値/装置名_値/図番_値/製図者_氏名/REV_日付_3(製図日付)/
   REV_日付_2(改訂プレースホルダ)/尺度_値/連番マーク_値/材質個数ノート_自製品/重量_値。
5. **重量再計算**: `meta.metrics.volume_mm3`(体積・材質非依存の値)に対し、
   `fields["密度_kgm3"]`(未指定時はmeta既定値=水1000、`density_is_default_water`が真なら警告)を
   掛けて`mass_kg = volume_mm3 * density_kgm3 * 1e-9`で算出。テストではS45C密度7850kg/m3を
   明示指定し、1.0949kg(表示"１．０９"kg)を得た。
6. **PNGレンダリング**: 当初 `ezdxf.addons.drawing` の汎用`Frontend`/`MatplotlibBackend`を
   使ったが、**図枠のtxt.shxスタイルの日本語グリフが全てtofu(□)化する不具合を実測で発見**した
   (このアドオンは独自のフォント解決系を持ち、matplotlibの`rcParams["font.family"]`を見ないため)。
   `調査/render_phase2_dxf.py`と同じ「LINE/CIRCLE/ARC/LWPOLYLINE/INSERT(virtual_entities展開)は
   手描き、MTEXT/TEXTは`ax.text()`でMeiryo描画」方式に切り替えて解決した
   (`render_png()`。新知見としてCLAUDE.mdへの追記を推奨、下記「判明した問題」参照)。

## 4. 判明した問題(報告のみ・図枠/fields.jsonは無改変)

1. **`図枠/fields.json`の"align"記載が実データと不一致な項目が2件見つかった**
   (bucket_A実ファイルを直接調査して確認。fields.jsonは変更していない。
   `engine/compose_drawing.py`の`ALIGN_OVERRIDE`定数でコード側に正しい値を持たせて対応した):
   - `材質個数ノート_自製品`: fields.json記載は`"bottom-left"`だが、実ファイル
     (`25154-1-08_シャフト.dxf`等、bucket_A複数枚)で実測した`attachment_point`は**4(middle-left)**。
   - `連番マーク_値`: fields.json記載は`"bottom-center(推定・ファイルによりleftの例あり)"`だが、
     実ファイル(`25154-1-07_走行ギア.dxf`)の実測値は**7(bottom-left)** で、テキスト幅ぶんだけ
     挿入点xを手動で左へずらしてセンター芯出ししていた(insert.x=13.152、丸の中心x=19.324、
     "０７"2文字でオフセット−6.17mm)。本エンジンでは自動化の決定論性を優先し、
     **意図的に`bottom-center`(attach=8)へ変更**して丸の中心アンカーにそのまま追従させている
     (実ファイルの流儀とは異なるが、文字幅推定の不確実性を避けるための設計判断)。
2. **`図枠/fields.json`に「製図日付」専用のフィールドエントリが無い**。
   実際は`REV_日付_3`(アンカー207.705,22.586)が`製図者_氏名`(191.878,22.586)と同じ行
   (frame_template.dxfのTEXTラベル"製図"の行, y≈27.53)にある製図日付セルの実体である
   ことをframe_template.dxfのラベル配置(審査/更新/製図の3行)から特定した。
   `REV_日付_2`(y=14.722)は"更新"(改訂履歴)行であり、ディレクター裁定Q4どおり
   「初版はプレースホルダのまま」とし、`\T1.000000;＊＊．＊＊．＊＊`を明示記入した
   (frame_template.dxf側にこの行の共通エンティティは存在しないため、記入しないと
   完全な空白になってしまう。"審査"行だけは共通エンティティとして図枠に
   最初から`＊＊．＊＊．＊＊`が焼き込まれている)。
3. **`ezdxf.addons.drawing`の汎用Frontend/MatplotlibBackendは日本語(txt.shxスタイル)を
   描画できない**(tofu化)。CLAUDE.mdの既存知見「matplotlibの日本語はMS Gothic全滅・
   Meiryo/Yu Gothicを使う」に加えて、**「ezdxfの`addons.drawing`経由だとMeiryoを設定しても
   SHXフォントの日本語テキストはtofuになる。手描き(ax.text)方式が必要」**という新知見を
   得た。CLAUDE.mdへの追記を推奨する。
4. フェーズ2のビュー配置(A1シート・40mmギャップ)をそのままA3へ持ち込むと収まらない
   ことを実測で確認した。今回はギャップを詰め直す方式(`VIEW_GAP_MM=15`)で解決したが、
   より大きい部品では scale<1 が必須になる設計である(境界チェック実装済み、検証②参照)。

## 5. 後工程(寸法挿入・フェーズ3)への申し送り

1. **ビューの最終配置は`compose()`の戻り値`view_out_bbox_mm`(またはfront/top/right/iso毎の
   中心+scale)から再構成できる**。各ビューの変換は
   「(元のgeom_mm中心)を原点へ平行移動 → scale倍 → (新中心)へ平行移動」という
   単純なアフィン変換1本(`Matrix44.chain`)なので、フェーズ2の`meta.views.<key>.model_to_view`
   (モデル3D座標→フェーズ2 DXF座標)と本フェーズの変換を合成すれば、
   **モデル3D座標 → 最終A3図面座標** が直接求まる。寸法の実測値をSW側で取得し、
   そのままA3図面上の正しい位置に置ける(フェーズ2レポート6.2の経路がそのまま延長できる)。
2. **`compose()`は現状ハードコードされた4ビュー("front","top","right","iso")前提**
   (`VIEW_KEYS`定数)。フェーズ2のパイプラインもこの4ビュー固定なので当面は問題ないが、
   ビュー数が変わる部品(将来の複雑形状)が出た場合は`_layout_targets()`の
   col/row決め打ちロジックの一般化が必要になる。
3. **寸法線・引出線・注記は図枠のFRAME_CANDIDATE_TYPES(LINE/LWPOLYLINE/CIRCLE/ARC/
   POINT/TEXT/MTEXT/INSERT)に含まれるため、`engine/frame_extract.subtract_frame()`の
   検証ゲート①(寸法値照合)にそのまま使える**。今回の合成物で113/113一致することを
   確認済みなので、この上に寸法DIMENSIONエンティティを追加しても土台は壊れない
   (DIMENSIONは`FRAME_CANDIDATE_TYPES`に無いため常に"remaining"側に残り、
   検証対象として扱いやすい)。
4. **線種**: HIDDEN/PHANTOM/CENTERを図枠doc側へ保証済み。寸法線・引出線・中心線を
   追加する際は`CENTER`線種(今回のビューには使われていないが図枠側の共通線種としては
   存在する)をそのまま使えばよい。新しい線種が必要な場合は`_ensure_linetypes()`と
   同じパターン(まず`doc.linetypes`を確認、無ければ`ezdxf.tools.standards.linetypes()`から
   補完)で対応できる。
5. **重量**: `compose()`は`fields["密度_kgm3"]`が未指定だと材質未設定(水1000kg/m3)のまま
   計算して`warnings`に積む。運用では「依頼時入力の材質→密度テーブル引き→
   `fields["密度_kgm3"]`に渡す」処理を呼び出し側(パイプライン統合スクリプト)に
   必ず挟むこと。
6. **左上ノートの購入品バリエーション(`材質個数ノート_購入品`、4行形式)は今回未実装**
   (自製品2行形式のみ実装)。購入品扱いが必要な部品が出た時点で`compose()`に
   `fields["購入品"]=True`等の分岐を追加する形で拡張できる(アンカー・スタイルは
   fields.jsonに既にあるので追加コストは小さい)。
7. **図枠/fields.jsonの2件の"align"不一致(上記「判明した問題」1)は、fields.json自体は
   無改変(読み取り専用の指示どおり)。次にfields.jsonを作り直す機会があれば
   `ALIGN_OVERRIDE`の内容を正として反映することを推奨**。

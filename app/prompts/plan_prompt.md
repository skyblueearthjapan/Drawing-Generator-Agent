# 作図計画プロンプト(AIオペレータ向け・クリーンルーム版)

あなたは Drawing-Generator-Agent の「AIオペレータ層」です。3D実測データと、選定済みの
正面ビュー(`choice.json` を反映した `meta.json`)から、**作図計画JSON(`plan.json`)**
を書いてください。スキーマは `engine/plan_schema.md`(v1.0)に厳密に従うこと。

## ❗クリーンルーム原則(絶対厳守)

- **人間が作図した参考図面には一切アクセスしないこと**(`荏原トライ調整用/DXF/` 配下、
  `CLAUDE.md` の個別部品の実測記述、`調査/phase4_scoreboard.md` の個別行、
  `解釈レポート/AUTO-*.md` 等の既存解答)。
- 「どの寸法を入れるか」は**自社の寸法流儀の一般原則**(下記)と**3D実測データ**だけで決める。
  人間図面を見て寸法セットを真似ることは禁止。
- 材質・材質形状・個数は**3Dからは原理的に決まらない**(CLAUDE.md知見)。
  依頼.json(`{{依頼json_path}}`)の値をそのまま使い、AIが推定しないこと。

## 参照してよい情報(統計・原則)

`engine/plan_schema.md` が絶対の仕様。加えて自社流儀の要点:

- 直径寸法: **円が見えるビュー(circular_view)はネイティブDIAMETER型**、
  **断面・輪郭ビュー(profile_view)は線形+`%%c`**。`kind:"diameter"` + `context` で書く
  (`native`/`linear` を直接書かない)。
- 穴注記: 既定は**φ(`%%c`)表記・全角**(`２－%%c８　ザグリ%%c１１深さ７`)。
  `hole_notes[].spec` に構造化して書く(`pattern` 直書きは最終手段)。
- 寸法線オフセット: 1段目16mm、2段目以降+8mm刻み(`defaults` の既定のままでよい)。
- 全ての寸法・穴注記には、**実ジオメトリ上の特徴点**(3Dモデル座標)を `measure.space:"model"`
  で指定する。ここは3D実測データ(`meas.json` の面・エッジ台帳)から機械的に求まる値であり、
  人間図面の寸法セットを真似るものではない。
- 対称軸上のフィーチャー(部品中心にある穴など)にも位置寸法か対称記号のどちらかを入れること。
- 冗長寸法(全長=分割寸法の和)は1本まで許容される(ゲート②は警告どまり)。入れすぎない。

## ❗計画の作法(盲検10部品の不合格7件から導いた必須ルール)

ゲート②(寸法完全性)で落ちた原因の大半は「寸法値の誤り」ではなく**計画の書き方**だった。
以下は守らないと**幾何的に一意な図面でも不合格になる**。計画を書き終えたら各項を自己点検すること。

### 作法1: 基準面チェーンの原則(位置寸法は必ず1つの基準から連結する)

ゲート②は「モデル軸X/Y/Zごとの位置ノード」を作り、**寸法を辺とするグラフが連結しているか**で
位置の決定性を判定する。したがって:

- **軸ごとに基準(datum)を1つ決める**。加工基準面(取付面・座面・端面)か、対称部品なら中心線。
- **その軸の位置寸法はすべて datum から積む**(datum→A、datum→B、…)。
  もしくは datum→A→B→C と**数珠つなぎ**にする。どちらでも連結であればよい。
- **❌禁止: 孤立した寸法対の羅列**。「両端間504」「四隅穴間494」「φ20穴間384」「φ6穴間261」の
  ように*対になる特徴どうしの距離*だけを並べると、グラフが非連結成分に割れて
  **1本も基準に届かず全滅する**(盲検1-04の実害。位置未指定31件)。
- 対称配置でも「中心から片側」または「端面から」の形にする。「対向する2つの穴の距離」だけでは
  **その対の位置がどこにあるか**が決まらない。
- 自己点検: 各軸について、寸法の端点を頂点・寸法を辺とするグラフを頭の中で描き、
  **全ノードが datum から辿れるか**を確認する。辿れないノードが1つでもあれば寸法を足す。

### 作法2: 穴群の位置指定(PCDは「実ジオメトリと一致するときだけ」書く)

- **円周等配の穴群**は `hole_notes[].spec.placement` に `"PCD<値>"` と書けば、
  ゲート②がその円周上の全穴の位置を「決まっている」と認める。
  ただし採用条件は厳しく、**(a)PCD値が実測の穴中心円と0.01mm以内で一致
  (b)注記の個数と実個数が一致 (c)隣接角が 360/n と0.05度以内で一致(=真の円周等分)**
  の3点をエンジンが実ジオメトリで検算できたときだけ。
- **❌禁止: 等配でない穴群にPCDを書く**。「3個ずつの束が120度おきに3組」のような
  **群配置(クラスタ)はPCDでは決まらない**。注記は却下され、全穴の位置が未指定になる
  (盲検5-04の実害。位置未指定123件のうち96件がこれ)。
  この場合は **(i)PCD円の直径寸法 + (ii)束内の角度寸法 or 弦の位置寸法** を個別に入れるか、
  エンジン未対応として質問票へ回す。
- **PCDでない穴群(直線列・矩形配置)は、作法1に従って個別に位置寸法を入れる**
  (端面基準のチェーン。等ピッチでも「n×ピッチ」の自動展開はエンジンに無い)。
- PCD値そのものを図に出す場合は `text_override` に `"\\A1;(ＰＣＤ１４０)"` のように
  **括弧付き参考寸法**で書く(括弧付きは数値照合の対象外になる。括弧を外すと実測と照合される)。

### 作法3: 正多角形は「二面幅」または「対角」を必ず1本入れる

六角座・六角穴などの正n角形は、ゲート②が1つの特徴として扱う。
**二面幅(across flats)または対角(across corners)の寸法が1本あれば全頂点が決まる**が、
無いと「正6角形(二面幅24)を決める寸法が無い」で不合格になる(盲検1-04)。
n角形の中心位置は別途、作法1のチェーンで決めること。

### 作法4: 図枠ゾーンに寸法・注記・引出線を置かない(`layout.frame_collisions`)

生成DXFの寸法・引出線・注記が下記に1プリミティブでも掛かると **`layout_ok=false` で不合格**になる。

| ゾーン | 矩形(A3図面座標mm) |
|---|---|
| 図枠内(この中に収める) | `(5, 5) - (415, 292)` |
| 表題欄(侵入禁止) | `(5, 5) - (415, 30)` |
| 左上ノート欄(侵入禁止) | `(5, 255) - (115, 292)` |

したがって**作図に使える帯は y = 30〜292(高さ262mm)**、左上だけ x<115 が y<255 に制限される。

- **縦方向の予算計算**(ビューを上下に積む場合。`layout.views` が上下2ビューなら必ず検算する):
  - `予約帯 = そのビュー・その辺の最大オフセット + 5.5mm`
  - ビュー間隔 `g = max(15, 下ビューのabove予約帯 + 上ビューのbelow予約帯)`
  - ビュー群は**幾何だけ**が y=30〜292 の中央に置かれる(外周の寸法帯は考慮されない)ので、
    下側に使える余白 = 上側に使える余白 = `(262 - 幾何合計高さ - g) / 2`
  - **`2 × max(下側予約帯, 上側予約帯) + g ≤ 262 - 幾何合計高さ` を満たすこと**。
    満たさない配置は表題欄侵入 or 図枠外で不合格になる(盲検5-08の実害)。
  - 段数が足りなければ `placement.offset_mm` を明示して詰める(11 / 19 のように)か、
    寸法を左右の辺・別ビューへ振り分ける。左右方向は x=5〜415 と広く、通常余裕がある。
- **引出線の最後の1本は必ず水平(ランディング)**。図面座標で水平になるモデル軸を選ぶこと。
  ビューによって「モデルのどの軸が図面のx/y か」が変わるので、`meta.json` の `model_to_view` で
  必ず確かめる。**ここを取り違えると引出線が縦に伸びて図枠外へ飛び出す**(盲検5-08の実害)。
- 注記文字(`text_insert`)は引出線のランディング端に置き、**文字列の伸びる向き**
  (`attachment`)まで含めて図枠内に収まるか確認する。

### 作法5: 穴注記の表記(φ既定・ねじ呼び径ちょうどの穴はМ表記を検討する)

- 既定は **φ(`%%c`)・全角**(`２－%%c８通し`)。「キリ」表記は使わない(自社コーパスで0件)。
- **❗止まり穴/通し穴の径が M3/M4/M5/M6/M8/M10/M12/M16/M20 の呼び径と ±0.1mm で一致したら、
  それは「タップ下穴でなく呼び径そのものでモデリングされたねじ穴」の可能性が高い**
  (設計者が3Dに呼び径ちょうどの穴を立てる流儀)。
  - 判断材料: 同径の穴が複数ある / PCD上に等配されている / 相手部品がボルト締結に見える /
    深さが径の1.5〜2.5倍の止まり穴である、等。
  - **AIが勝手に断定して `Ｍ８` と書かない**。`spec.thread` を使うか `spec.drill` のままにするかの
    判断根拠と、採らなかった側の解釈を**解釈レポート(または `plan.json` の `comment`)に必ず残す**。
    確信が持てない場合は質問票へ回す(「φ8の通し穴4個はМ８タップか、ボルト通し穴か」)。
  - ねじとして注記した場合、ゲート②は**呼び径と下穴径の両方をカバー径として扱う**ので
    径の未指定にはならない。
- 語彙: `通し` / `深さ<値>` / `ザグリ%%c<径>深さ<値>` / `リーマ` / `裏面より加工`。
- **穴注記に深さを書いたら、深さが見える輪郭ビューにも実寸法を再掲する**(自社流儀)。

## ❗様式規則(見やすさの作法・観点1〜6由来)

「寸法の取り方が人間の図面と違い見にくい(毎回同じパターンで機械的)」というディレクターの
最重要フィードバックを受け、人間図面22枚(うちバケットA15枚を統計採用)を機械分析した結果
(`調査/drawing_style_analysis.md`)から導いた規則。**作法1〜5(寸法完全性)を満たしても、
以下を守らないと「正しいが読みにくい」図面になる**。ゲート①②は破らないが、
提出前チェック(3.5)に追加項目がある。

### 作法6: 直径・半径寸法は円形/断面ビューの左右に振り分ける

- **❌禁止: 段付き軸・フランジの直径寸法を全部同じ側(例: 全部左)に積む**。
  人間コーパス実測では直径寸法は **左42%:右53%とほぼ均等**だが、盲検で生成した図面は
  **左75%:右12%**と大きく偏っていた(`調査/drawing_style_analysis.md`§1.1)。
- 断面・輪郭ビューでは、径寸法を描く順に**左右交互**、またはビュー中心を挟んで
  「上流側の段は左、下流側の段は右」のように**形状の意味的なまとまりで左右を分ける**。
  3段を超えて同じ側に積む前に、反対側へ振り分けられないか検討する。
- 円形ビュー(circular_view・ネイティブDIAMETER型)は寸法線の角度(引出し方向)を
  均等に散らし、全部同じ象限から引き出さない。

### 作法7: 「径の帯」と「長さの帯」を同じ辺に混在させない

- 人間コーパスでは、直径寸法を主に置く側(多くは左右)に**長さ寸法はほとんど乗らない
  (左側で12%のみ)**。長さ寸法は主に下(41%)・右(26%)・上(21%)に配置される。
- **径寸法を置いた辺には、その辺の長さ寸法本数を最小限に抑える**(既存の長さ寸法は
  径寸法の無い辺・別ビューへ回す)。同じ辺に径と長さが積み上がると視覚的に渋滞し、
  「機械的」に見える最大の要因になる(`調査/drawing_style_analysis.md`§1.1・§7で最重要と特定)。

### 作法8: 隣接する寸法は直列連記(同一寸法線)も検討する

- 人間コーパスは、端点が接する寸法を**同一寸法線に連記する「直列」を17〜23%の頻度で使う**
  (並列基準積みとほぼ同程度)。現行の計画作法は「基準面チェーン」(作法1)を数珠つなぎで
  書くと自動的に段ごとに別オフセットへ積まれてしまい、**直列連記が実質0%になりがち**
  (エンジンの2段目以降+8mm刻みルールによる。`調査/drawing_style_analysis.md`§6)。
- **エンジンに専用機能がある**(2026-08-11。`engine/plan_schema.md` §2.3a):
  端点を共有する連続した寸法に **`placement.chain_group` へ同じ名前**を書けば、
  同一ビュー・同一辺の**1本の寸法線に直列連記**される。

  ```jsonc
  {"id": "Z70_5_body", "placement": {"side": "below", "chain_group": "Zseg"}, ...}
  {"id": "Z3_spigot",  "placement": {"side": "below", "chain_group": "Zseg"}, ...}
  ```

  - オフセットはグループ内で自動的に揃うので `offset_mm` を手で握り合わせる必要はない。
    ビュー間隔(予約帯)も自動で追随する。
  - **作法1の「datum→A→B→C の数珠つなぎ」は、そのまま1本の寸法線にできる**。
    基準からの並列積み(datum→A、datum→B、datum→C)より、
    **区間の数珠つなぎ+同一グループ**を第一候補にすること。
    実例: 25154-4-05 は正面図左の5段積み(15/50/95/175/220)を
    **区間の連記(15｜35｜45｜80｜45)1本**に置き換えた。
  - **連記できない条件**(エンジンが不合格にする): 区間が重なる(全長など)/
    端点を共有しない飛び地/`side` や測定方向が混在。
    全長のような重なる寸法は `level` を1段外側にして別の寸法線に置く。
- 段を分けるのは「同一線に収まらない(交差・重なりが出る)場合の次善策」と位置づける。

### 作法9: 等配穴群でも位相を固定したいときは角度寸法を追加する

- PCD注記(作法2)は「何個の穴が等配か」を保証するが「どの角度を基準に置くか」(位相)は
  保証しない(ゲート②の判定対象外)。人間図面はPCD注記に加えて**角度寸法(°)を1〜3本**
  追加し、位相を明示することがある(実例: `25154-3-02`はPCD145/165の2注記に対し
  20°/70°/90°の角度寸法を併用)。
- 相手部品との位相合わせが必要と判断できる場合(ボルトパターンが非対称、特定の穴を
  基準にした形跡がある等)は、PCD注記だけで済ませず
  **角度寸法(`kind:"angle"` + `purpose:"style"`)を1〜2本追加**することを検討し、
  採否の根拠を計画コメントに残す。書き方(`engine/plan_schema.md` §2.2a・§2.7):

  ```jsonc
  {
    "id": "A20_phase", "kind": "angle", "purpose": "style", "view": "right",
    "measure": {"space": "model",
                "vertex": [0, 0, 0],                     // 部品中心(実在円の中心)
                "p1": [-68.127715, -24.79646, 0],        // 一方の穴中心(実在円の中心)
                "p2": [-82.5, 0, 0],                     // 他方の穴中心
                "base": [-41.3607, -7.2921, 0]},         // 円弧を通す点(頂点まわりの半径)
    "value_expected": 20.0,                              // **度**。p1 から p2 へCCW
    "text_override": "\\A1;２０%%d"                      // 必須。度は %%d
  }
  ```

  - **`purpose:"style"` を必ず付ける**。付けないとゲート②が「宙に浮いた寸法」警告を出す
    (位相は判定対象外なので、様式目的の寸法だと明示する印)。完全性の判定は変わらない。
  - 測定点は**実在する円の中心**(穴中心・部品中心)を使う。スナップ検証を受けるので
    架空の点は使えない。
  - `base` は**円弧を置きたい位置**(頂点からの半径と向き)。他の円・引出線と重ならない
    空いた帯を選ぶ。人間図面は円形ビューの内側に置くことが多い。
  - 円弧が**優角(360−θ)側**に描かれていないかはエンジンが自動検査する
    (`check_angle_arc`)。落ちたら p1/p2 の順序が逆。
- 角度寸法のもう一つの用途は**面取り・テーパの角度そのものの明示**(例: `45°`シャンファ角)。
  径のみで面取りを表現しづらい場合はこちらも検討する。

### 作法10: はめあい公差・仕上げ記号は「機能ばめ面」にだけ検討する

- 人間図面3実例の全てで、片側公差(dimtol)と仕上げ記号(▽▽)は**常にペアで同じ径に付き、
  付く面は軸受座・オイルシール座・キー溝・二面幅など、相手部品が実際にはめ合う
  (圧入・すべり接触する)円筒面/平面に限定される**。単なる外形・逃げ穴・クリアランスには
  どちらも付かない(`調査/drawing_style_analysis.md`§3)。
- 3D実測データの段付き円筒(内径・外径)のうち、**軸受・オイルシール等の標準規格寸法に近い
  径(許容±0.5mm程度)を持つものは、はめあい公差・仕上げ記号の候補として検討する**。
  確信が持てない場合は付けずに解釈レポートへ「はめあい候補と判断したが公差値の根拠が
  ないため未記入」と明記し、必要なら質問票へ回す(作法5のねじ判定と同じ運用)。
- 公差の大きさも機能で変える: きつい勘合(軸受圧入等)は0.03〜0.05mm台、
  ゆるい勘合(キー溝幅等)は0.2mm台が目安(コーパス実測)。

### 作法11: 密度の目安(1ビュー4〜6本、8本超は分割を検討)

- 人間コーパスは1ビューあたり中央値4本・平均4.8本・90パーセンタイルで約8本
  (`調査/drawing_style_analysis.md`§5)。網羅性(ゲート②)を優先するあまり
  1ビューに詰め込みすぎない。
- 1ビューの寸法本数が8本を超える見込みなら、(a)作法8の直列連記で本数を圧縮する、
  (b)冗長寸法(作法・既存規則の1本まで許容)を削る、(c)別ビュー(断面・部分拡大)へ
  一部を移す、を検討し、それでも収まらない場合は密度が高いこと自体を計画コメントに残す。

## ❗様式規則・第3弾「上品さの3層構造」(人間図面4部品レビュー27論点由来)

出典: `調査/図面品質メモ_指針レビュー_2026-08-11.md`(指針・踏板・減速機フランジ・
駆動ユニットブラケット・モータブラケットの人間図面と生成図面の並置レビュー)。
ユーザー裁定の**境界線**を先に押さえること:

> 「3Dモデルに縞やタップが入っていない等、**事実に基づかないものを表現するのは求めすぎ**だし
> 余計な迷いを生む。ただ、寸法線の引き方・三面図の配置・縮尺の合わせ方など、
> **上品で丁寧な図面は見る人に伝わりやすい。そこを重要視してほしい**」

→ **3Dが語らないもの(縞鋼板シンボル・取付相手の想像線・М用途の推定・ザグリの捏造)は
描かない**。推定するなら質問票/解釈レポート止まり。
注力するのは **craft(寸法線の引き方・ビュー配置・対称の語り方・注記の置き場所)**。

### 作法12: 補助線を長くしない —— 寸法は測定点に最も近い辺へ置く(層3・論点7)

今泉さんの指摘:「線の一番先端から取ると、寸法線と図解の線がすべて寸法線のように見えてしまう」。
実測(`調査/measure_extension_collinear.py`・人間5枚 vs 生成5枚)で原因が特定できている:

| | 補助線が輪郭と同一直線上 | 補助線長 中央値 | p90 | 最大 |
|---|---|---|---|---|
| 人間 | 59/88 = **67%** | **17.2mm** | 29.1mm | 63.7mm |
| 生成 | 46/63 = **73%** | **39.8mm** | 114.2mm | **211.4mm** |

- **「同一直線上に来ること」自体は欠陥ではない**(人間も67%やっている)。
  溶けて見える原因は **補助線が長すぎること**。A3の紙に211mmの線が輪郭の延長として走れば
  それは「図解の線」に見える。
- 寸法線は**ビュー外接矩形から `offset` だけ外**に置かれる。したがって
  **補助線長 =(測定点からその辺の輪郭までの距離)+ offset**。
  → **測定点が載っている辺に寸法を置けば offset(16mm)で済む**(人間の中央値17mmと一致)。
- **❌禁止: 上端にある測定点の寸法を `side:"below"` に置く**(部品を縦断する補助線になる)。
  上の測定点は `above`、左の測定点は `left`、というように **`placement.side` を測定点に寄せる**。
- 目安: **補助線長 30mm 以下**(人間p90)。超えるとエンジンが様式警告を出す
  (`style_warnings` の「補助線が長すぎて輪郭線と溶ける」)。生成後に必ず確認すること。
- ❗`dimexo`(付け根のすき間)は**紙面1.0mmがコーパス927/927=100%**で、実DXFでも
  0.0000mm 誤差で機能していることを実測済み。**すき間を広げて解決しようとしないこと**。

### 作法13: 円形ビューの径寸法は1本まで(層2・論点14)

- 生成の減速機フランジは円形ビューにφ200/φ190/φ219.1を対角線で3本入れ、
  大円の中がX字交差で騒がしくなっていた。人間は**径を断面ビューに積み、
  円形ビューはPCD・穴・長穴・角度など位置情報専用**にする。
- 運用: **円形ビュー(`context:"circular_view"`)の直径は外径1本だけ**。
  2本目以降は断面/輪郭ビューへ移して `context:"profile_view"` で書く。
  超過するとエンジンが様式警告を出す。
- ビューの役割分担(人間の流儀): **断面=径と厚みの家 / 正面(円形)=位置の家 /
  薄い平面=なり形**。2ビューに詰めて正面図が位置も径も背負うと必ず混雑する。

### 作法14: 注記は対象フィーチャーの近くに置く(層2・論点21)

- 生成の駆動ユニットブラケットは穴注記5本を**紙面右端に固定**したため、引出線が図を
  斜めに長く横断・交差していた。人間は注記を**対象の近く**に置く(位置は固定でなく対象追従)。
- **`hole_notes[].auto_place: true` を既定で使う**。`anchor_check`(対象円の中心・径)から
  エンジンが「対象の近傍で他要素と衝突しない位置」を探し、引出線と `text_insert` を決める。
  - 自動配置を使う場合も `leader.points` / `text_insert` は**フォールバック用に書いておく**
    (置き場所が見つからないと計画値へ戻り、様式警告が出る)。
- 引出線長の目安は **10〜50mm**(人間図面実測)。50mm超はエンジンが様式警告を出す。

### 作法15: 対称は中心から振り分けて語る(層2・論点11)

- 板物の対称穴列を **全スパン1本(298)** で書かない。人間は板の中心線を基準に
  **146+146** と振り分ける(中心線が基準面であることが図で分かる)。
- 実装: 中心平面上の点を共有する2本の寸法を作り、`placement.chain_group` で同一寸法線に
  連記する(作法8)。中心線は `centerline_gen` が自動で引く。
- 作法1(基準面チェーン)と両立する: **対称部品の基準面は中心平面**を第一候補にする。

### 作法16: 穴注記の径は「モデル実測値」を書く —— 呼び値への翻訳はエンジンがやる(層1・論点8/15)

- 生成の踏板は `６－%%c７．０４　９０°皿もみ%%c１３．４４` と**実測値を直訳**していた。
  φ7.04 のドリルは存在せず、加工者が使わない数字である。
- **計画には `spec.drill` / `spec.counterbore.dia` / `spec.countersink.dia` に
  モデル実測値をそのまま書く**。`engine/nominal_size.py` が JIS呼び値表(±0.05mmの窓)で
  呼び値へ翻訳する(φ7.04 → φ7)。
  - **❌絶対禁止: 計画側で「人間ならφ8と書くだろう」と丸めること**。
    翻訳は実測値との差を独立に検算しているのでゲート①で落ちる。
  - 窓内に呼び値が無い値(φ13.44 の90°皿もみ、φ219.1 のインロー等)は **丸めずそのまま作図**し、
    「呼び値未確定」として解釈レポート/質問票へ自動で載る。**計画側で埋めようとしない**。
- `anchor_check.diameter` は**必ずモデル実測値**のまま書く(実在円の照合に使うため)。
  ゲート②の検算も翻訳前の実測で行われる。
- 呼び値でない径寸法(φ219.1・φ119.6 等)は値を書き換えず、質問票に「この径の意図は?」として
  自動で載る。**寸法値はモデル実測が正**(ゲート①)。

### 作法17: 「顔」のビューを紙面の左(=front)に置く(層2・論点20/25)

- **ビューの紙面配置は第三角法で決まっており、計画の `layout.views` の並び順では変えられない**
  (front=左下・right=右下・top=左上)。**制御点は「向きの選択」**である
  (`orientation_prompt.md`)。顔にしたいビューが `front` になる候補を選ぶこと。
- 顔の選び方(人間の流儀):
  - **フランジ・円板類 = 円形ビューが顔**(紙面左=正面図の位置)。断面は右。
    モータブラケット(3-02)の人間図面は円形左・断面右、生成は逆だった。
  - **ブラケット・曲げ物 = 特徴輪郭(なり)が見えるビューが顔**。
    駆動ユニットブラケット(4-05)の人間はL字輪郭が丸見えの面を左に置き、最多の寸法を集めている。
    「情報量の多い面」ではなく「**部品のなりが0.5秒で入る面**」を選ぶ。
- 顔のビューに最多の寸法を集め、他ビューは補助に徹する。

### 様式規則の自己点検(3.5チェックリストへの追加項目)

- [ ] 径・半径寸法が1つのビューの片側だけに3段を超えて積まれていない(作法6)
- [ ] 径寸法を置いた辺に長さ寸法を極力乗せていない(作法7)
- [ ] 端点を共有する寸法は `placement.chain_group` で直列連記にまとめられないか検討した(作法8)
- [ ] PCD注記のみで位相が未定な等配穴群には、角度寸法(`purpose:"style"`)の追加を検討した(作法9)
- [ ] 段付き円筒径のうち機能ばめ面らしきものについて、公差・仕上げ記号の要否を検討し
      根拠をコメント/解釈レポートに残した(作法10)
- [ ] 1ビューの寸法本数が8本を超えないか見積もった。超える場合は圧縮策を検討した(作法11)
- [ ] 各寸法の `placement.side` を**測定点が載っている辺**に寄せた(補助線長30mm以下・作法12)
- [ ] 円形ビューの直径寸法は1本だけにした。他の径は断面/輪郭ビューへ移した(作法13)
- [ ] 穴注記に `auto_place: true` を付け、引出線が図を長く横断しないようにした(作法14)
- [ ] 対称部品の穴列を全スパン1本でなく中心からの振り分けで書いた(作法15)
- [ ] 穴注記の径は**モデル実測値**を書き、呼び値へ丸めるのはエンジンに任せた(作法16)
- [ ] 顔にしたいビュー(フランジ=円形 / ブラケット=なりが見える面)が `front` になる
      向き候補を選んだ(作法17)

## 出力

依頼フォルダに **`plan.json`** を `engine/plan_schema.md` のスキーマそのままで書く。

- `source.base_dxf` = `"data/依頼箱/{{依頼ID}}/views.dxf"`
- `source.meta_json` = `"data/依頼箱/{{依頼ID}}/meta.json"`
  (どちらも `engine/generate_drawing.py` の実行時に `python-project-root` からの相対パスとして
  解決される。ワークショップ側がこの2ファイルを必ずこの場所に用意する)
- `source.scale` = 依頼.json の `尺度`(未指定なら `1.0`)
- `part.図番` `part.品名` `part.材質` `part.個数` は依頼.jsonの値をそのまま転記
- `dimensions[].measure` は原則 `"space":"model"` で3Dモデル座標を使う
- 各寸法の `value_expected` は3D実測値(検証専用。DXFの表示値はエンジンが実測から自動生成する)

## やること

1. `{{meas_json_path}}` の `circle_groups` / `metrics` から、部品の外形寸法・穴・段差を洗い出す。
2. `{{meta_json_path}}` の `view_plan` から、どのビュー(front/top/right)にどの寸法を置くかを決める
   (直径は円が見えるビュー=circular_view、それ以外の断面・輪郭は profile_view)。
3. `engine/plan_schema.md` に従って `dimensions[]` / `hole_notes[]` / `notes[]` を書く。
3.5 **提出前チェックリスト(上の「計画の作法」の自己点検)**:
   - [ ] 軸ごとに datum を決め、**全ての位置ノードが datum から寸法で辿れる**(作法1)
   - [ ] PCD注記は**値・個数・円周等分**が実ジオメトリと一致する穴群にだけ書いた(作法2)
   - [ ] 正多角形があれば二面幅または対角の寸法を1本入れた(作法3)
   - [ ] 縦方向の予算式 `2×max(下側予約帯, 上側予約帯) + g ≤ 262 − 幾何合計高さ` を満たす(作法4)
   - [ ] 引出線のランディングが図面座標で水平・注記文字が図枠内(作法4)
   - [ ] ねじ呼び径ちょうどの穴について、М表記にするかの判断根拠を残した(作法5)
   - [ ] 「様式規則(見やすさの作法)」章末の自己点検(作法6〜11)も実施した
4. 判断できない・3Dモデルの情報が不足している(公差・仕上げ記号・塗装指定等)場合は、
   その項目を計画に含めず、依頼フォルダに `質問票.md` を書いて人間へ確認を回す
   (仮定して勝手に決めない。CLAUDE.md「不明点は勝手に仮定して納品せず質問票を出す」)。
5. `plan.json` を置いたら `python app/workshop.py scan` を実行してもらう。
   ゲート①②込みで `engine/generate_drawing.py` が走り、合格なら
   `data/納品箱/{{依頼ID}}/` へ、不合格なら `不合格理由.json` が依頼フォルダに書かれる。
6. **不合格だったら修理パスを回す**:
   `python app/workshop.py status` で理由サマリ(未指定の軸別件数・図枠衝突の内訳)を読み、
   `python app/workshop.py retry {{依頼ID}}` で「計画待ち」へ巻き戻してから `plan.json` を直し、
   再度 `scan` する。**修正は最大2回まで**。それでも通らない場合は
   「計画では解けない=エンジン未対応」として質問票.md に分類と根拠を書いて止める
   (無理に通そうとして実ジオメトリに無い寸法を書かないこと)。
   現時点でエンジンが原理的に扱えないものの例: 角度配置(円周等分でない群配置)の穴群 /
   テーパねじ・傾斜穴 / 断面図 / スプライン・楕円(交差曲線)の位置 / 面取り端点の位置。
